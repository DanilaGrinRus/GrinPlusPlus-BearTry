# Архитектура — нода этого форка

Эта страница описывает модуль ноды (`GrinNode`) в дереве
`node-beta.1-candidate`. Кошелёк и UI вне области. Описание основано на исходниках
этой метки и зафиксированных прогонах; непроверенное поведение помечено.

## 1. Карта компонентов

| Слой | Основные компоненты | Исходники |
|---|---|---|
| Точка входа | разбор опций, загрузка config, логирование, главный цикл, штатное завершение | `src/Server/Main.cpp`, `src/Server/opt.h` |
| Сборка ноды | ранний health-сервер, открытие цепи/P2P, полный REST/RPC | `src/Server/Node/Node.cpp`, `NodeRestServer.cpp` |

## 2. Старт и перезапуск

Порядок намеренный: процесс должен быть наблюдаем, пока открывается база
размером в несколько GB.

1. Разбор опций и загрузка `server_config.json` (или defaults). Создание
   каталогов данных и логов.
2. Запуск раннего HTTP-listener с `GET /v1/health`, возвращающим
   `{"status":"starting"}`. На профиле первый 200 — примерно через
   `0,56–0,62 с`.
3. Открытие цепи: файлы цепи, header MMR, RocksDB block DB, TxHashSet manager.
   Проверка или перестройка KernelIndex, если он отсутствует, привязан к другому
   tip или вышел за доверенные пределы расширения.
4. Создание полного REST/RPC-сервера (все `/v1`, `/v2/foreign`, `/v2/owner`) и
   перевод health в `ready`. `/v1/status` существует только с этого момента.
5. Запуск P2P и state machine синхронизации. `ready` не означает
   `fully_synced`: на профиле `ready` предшествовал полной синхронизации
   примерно на 19–25 с.

Перезапуск на согласованном состоянии открывает файлы, сверяет индекс ядер с tip
и продолжает. Перезапуск на несогласованном или частично записанном состоянии
должен восстановиться из последнего атомарного checkpoint или отказать
fail-closed, а не публиковать частичное состояние. Потеря питания и реальный
отказ хранилища **NOT VERIFIED**; kill-harness покрывает только принудительное
завершение процесса.

## 3. Первичная синхронизация и state machine

Фазами управляет `SyncStatus`/`StateSyncer`:

1. **Пиры.** DNS-seeds и peer book создают исходящие соединения; seeder
   стремится к min/max пиров и терпит отдельные отказы. Медленный или упавший пир
   ротируется без бана. Запросы заголовков ограничены одним за 200 мс.
2. **Заголовки.** Header sync продвигает цепь заголовков и header MMR к высоте
   сети. `SYNCING_HEADERS` отдаёт текущую/высшую высоту.
3. **Состояние.** Если нода сильно отстала, нужен snapshot состояния
   (TxHashSet). Предпочтительный путь — **PIBD**. Если capable-пиров нет или
   PIBD не может продолжить, нода откатывается на legacy `txhashset.zip`
   (`SYNCING_TXHASHSET`, байтовые счётчики).
4. **Проверка и активация.** Скачанное состояние проверяется (история ядер,
   суммы ядер, rangeproof, подписи ядер), затем устанавливается. Для
   установленного tip строится KernelIndex.
5. **Догон.** `SYNCING_BLOCKS` запрашивает оставшиеся блоки, применяет их и
   сверяет итоговый tip.
6. **Полная синхронизация.** `NOT_SYNCING` означает, что высота догнала сеть;
   legacy-поле `/v1/status` показывает `FULLY_SYNCED`.

Наблюдаемый живой прогон Floonet на объединённой сборке (`16C24DB4…`) прошёл
именно эту последовательность: заголовки `0 → 3 324 027`, PIBD `4998/4998`
сегментов, проверка состояния около `1987 с`, поколение KernelIndex 2 с
`3 356 610` ядрами, догон до `3 324 064`, финальная высота `3 324 082` после
следующих блоков.

## 4. PIBD: сегменты, пиры, resume и восстановление

PIBD заменяет монолитный ZIP независимыми сегментами MMR и следует wire-формату
Rust Grin 5.5.2.

- **Высоты сегментов** (`PibdParams.h`): bitmap — `2^9` чанков, output/
  rangeproof/kernel — `2^11` листьев. Запросы ограничены
  (`SEGMENT_REQUEST_COUNT = 15` в полёте, таймаут `20 с`, небольшой кеш).
- **Загрузка.** `PibdDownload`/`PibdSegmentService` запрашивают недостающие
  сегменты у capable-пиров, проверяют payload по ожидаемым корням/размерам и
  собирают output/rangeproof/kernel/bitmap MMR в staging-каталоге.
- **Планировщик.** `PibdScheduler` назначает запрос наименее загруженному пиру в
  пределах глобального и на-пир лимита. Ошибка отправки освобождает назначение;
  отключение освобождает назначения пира; ответ от неожиданного пира
  отклоняется без потери сегмента; проверенные поздние ответы принимаются, если
  назначения уже нет; дубликаты устаревают. Политики покрыты детерминированной
  матрицей тестов. Живое враждебное поведение на уровне P2P-банов — **NOT
  VERIFIED**.
- **Resume.** Прогресс сохраняется на диск; перезапуск может продолжить с
  последних валидных сегментов. Точная матрица перезапуска на каждой стадии —
  **PARTIAL/NOT VERIFIED** на кандидате.
- **Активация.** Полное staging-состояние несёт marker завершения и
  устанавливается двумя rename с marker-файлом (`pibd_activation.pending`). При
  смерти процесса во время swap следующий старт либо завершает активацию, либо
  восстанавливает backup; live-файлы никогда не усекаются на месте. Неудачное
  восстановление привязывается к horizon hash через
  `pibd_state.recovery_failed`, чтобы нода не повторяла невозможное
  восстановление бесконечно.
- **Legacy fallback.** Если PIBD недоступен, остаётся `txhashset.zip` с
  распаковкой в staging и атомарным swap. Это отдельный путь со своей историей
  доказательств.
- **Отдача архива** — opt-in диагностический режим
  (`GRINPP_PIBD_ARCHIVE_SERVING=1`), не часть обычной работы; публичная отдача
  PIBD — NOT VERIFIED.

## 5. Жизненный цикл KernelIndex

`KernelIndex` отображает excess commitment ядра в позицию PMMR и высоту блока,
чтобы `get_kernel` и валидация не сканировали весь kernel MMR.

- Индекс **привязан к поколению и конкретному tip**: tip hash/height, kernel
  root, kernel count и entry count. Lookup используется только при совпадении
  всех значений с текущим tip.
- При применении блока индекс обновляется в той же write-транзакции, что и блок:
  новые позиции ядер добавляются, reorg откатывает затронутые позиции. Если
  транзакция append/rewind падает, старое состояние сохраняется, а запись цепи
  завершается fail-closed — частичный индекс не публикуется.
- При старте `Ensure` проверяет сохранённое состояние. Если сохранённый tip —
  проверенный предок в ограниченных пределах (сейчас 4096 высот / 32768 ядер),
  добавляются только недостающие ядра одной транзакцией. Иначе выполняется
  полный rebuild с публикацией нового поколения.
- Orphan-блоки восстанавливаются после commit (`EnsureKernelIndexLocked`), чтобы
  валидный orphan не продвинул цепь при устаревшем индексе.
- Rebuild состояния ~3,36 млн ядер: `101 870 мс` записи, `16 435 мс` commit,
  `3 833 мс` read-back; пик рабочего набора `5 715 MB`. Chunked rebuild,
  снижающий пик, — **PLANNED**, не реализован.
- Fault injection на границе транзакции индекса и принудительные kill покрыты
  тестами. Реальный отказ RocksDB, post-commit и потеря питания — **NOT
  VERIFIED**.

## 6. Валидация и выбор потоков

- Заголовки проверяются на связность цепи, PoW, листья и внутренние узлы header
  MMR, timestamp, version и total difficulty. Валидация header/MMR занимает
  `57,8–88,0 с` на профиле ~3,32 млн заголовков; сохраняющее целостность
  параллельное ускорение чанками — **PLANNED**.
- Rangeproof проверяются пакетами (`RangeProofBatchVerifier`). Default — **1**
  поток. `GRINPP_RANGEPROOF_WORKERS=auto` включает ограниченный автоматический
  выбор по affinity процесса, физическим ядрам, доступной памяти и лимитам
  Windows Job Object; `GRINPP_RANGEPROOF_WORKERS=1|2|3|4|…` задаёт число явно.
- Учёт Job Object использует per-process и job-wide committed memory, берёт
  минимальный остаток, обрабатывает `< 1 MiB` точно и уходит в консервативный
  путь с одним потоком, если лимит неизвестен. Полный benchmark 1/2/3/4/auto —
  **OPEN**; default остаётся 1.
- Локальная ошибка при обработке блока (например, отказ записи индекса) не
  должна банить пира: валидность пира неизвестна. Это покрыто контрактным тестом
  BlockPipe.

## 7. FastInit header checkpoint (экспериментально)

`HeaderStateCheckpoint` — **экспериментальное opt-in** ускорение проверки
заголовков. Не часть обычного старта и не должно подаваться как production.

Модель доверия в текущем виде:

1. Checkpoint содержит полное состояние цепи заголовков и принимается только
   после полной проверки (листья и внутренние узлы MMR, последовательность,
   version, timestamp, previous root, монотонность difficulty, префикс
   подтверждённой цепи, размеры chain/MMR).
2. **Первый** checkpoint пишется только при явном
   `GRINPP_HEADER_CKPT_BOOTSTRAP=1` **и** опубликованном aggregate anchor в
   `GRINPP_HEADER_CKPT_TRUST_ANCHOR`. Без anchor нода пишет
   `header_checkpoint_not_written reason=no_trusted_anchor` и продолжает полную
   проверку.
3. Существующий checkpoint используется только при совпадении метаданных с
   файлами цепи; иначе — fallback на полную проверку.
4. После успешной синхронизации checkpoint может обновляться. Измеренный refresh
   на профиле — `9,56 с`; обычный перезапуск с checkpoint — `7,8 с`.
5. При убийстве процесса во время refresh предыдущий checkpoint остаётся целым
   (наблюдалось однажды: 31 081 байт, hash не изменился).

Ограничения: реальный reorg на валидной альтернативной ветке, поведение при
профильной блокировке и продолжение после kill не проверены. Цифры — не
финальная контролируемая серия. Любой результат FastInit считать
**EXPERIMENTAL / NOT VERIFIED**.

## 8. Раскладка на диске

Корень по умолчанию: `%USERPROFILE%\.GrinPP\<NETWORK>` (переопределяется
`DATA_PATH` в config). Всё ниже — под этим корнем.

| Путь | Содержимое |
|---|---|
| `server_config.json` | Конфигурация (если не используется `--config-path`) |
| `.api_secret` | 64-hex API-секрет, owner-only; создаётся при первом старте |
| `LOGS\` | Логи ноды |
| `NODE\CHAIN\` | `confirmed.chain`, `candidate.chain`, `header_mmr.bin`, `chain.checkpoint` (атомарный checkpoint), опционально `header.ckpt` (FastInit) |
| `NODE\DB\` | RocksDB block/kernel DB |
| `NODE\TXHASHSET\` | Живое состояние: `output/`, `rangeproof/`, `kernel/` MMR, `txhashset.bin` и связанные файлы |
| `NODE\pibd_staging\` | Незавершённое PIBD-состояние (та же раскладка) |
| `NODE\pibd_activation.pending` | Marker незавершённого swap активации |
| `NODE\TXHASHSET\pibd_state.complete` | Marker завершения внутри проверенного staging/live-состояния |
| `NODE\TXHASHSET\pibd_state.recovery_failed` | Привязанный marker, запрещающий бесконечное восстановление одного horizon |
| `TOR\` | Данные Tor при включённом Tor |
| `logs\` рядом с EXE | Диагностические логи; fallback в `LOGS\node-diagnostics`, если каталог не записывается |

Профили не переносимы между машинами без осторожности: важны блокировка базы,
ACL API-секрета и абсолютные пути в config. Никогда не копируйте профиль с
реальными ключами кошелька в тестовую среду.

## 9. API и границы доверия

- HTTP-сервер слушает локально. PRIVATE/ADMIN требуют API-секрет и loopback
  `Host`/`Origin`; PUBLIC — только чтение. См. [API.ru.md](API.ru.md).
- Ввод пиров недоверенный: у парсеров сообщений явные лимиты, неверные или
  чужие по корню сегменты отклоняются fail-closed, а пир не банится за локальную
  ошибку обработки.
- Нода никогда не логирует API-секрет, seed-слова и приватные ключи. Не
  добавляйте их в диагностику.

## 10. Известные архитектурные ограничения

- Нет проверенного прогона Mainnet; нет проверки потери питания и реального
  отказа диска.
- Публичный reorg только синтетический; реальный сетевой reorg — NOT VERIFIED.
- Полный benchmark потоков и автоматический выбор default открыты.
- Пик памяти rebuild KernelIndex (~5,7 GB) и время проверки заголовков
  (~58–88 с) — нерешённые вопросы производительности.
- FastInit и PIHD экспериментальные/запланированные и выключены по умолчанию.
- Кошелёк и UI — отдельные непроверенные треки.
